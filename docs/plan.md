# Midnight Proof Kit 기획과 진행 상황

이 문서 하나만 읽고 작업을 이어 갈 수 있게 쓴 기획서입니다. 원래 기획을 그대로 옮기고, 진행 중에 정한 것은 "결정 기록"에 날짜와 함께 적었습니다. 기획을 바꾸는 일은 결정 기록에 남기기 전에는 하지 않습니다.

**용어**
- **기준선 실험** (1)~(3): 우리 도구 없이/있이 계약을 만들어 구멍 수를 비교하는 실험(8절). 이 실험의 "시나리오 4개"는 만들 계약의 주제입니다.
- **래칫 기준선 파일** `privacy-baseline.json`: 첫 실행 결과를 저장해 두고 이후 새 위험만 실패로 내기 위한 파일(5절).
- **시나리오 쌍**: `bench/scenarios/`의 구멍 판 / 고친 판 계약 한 쌍(9절).
- **누출 설명** `privacy-spec.json`: 무엇이 드러나도 되는지 적은 파일(design-guide 2장, 5장).

## 1. 목표

**문제.** Midnight로 개발해 보면, 기획대로 회로를 설계한 뒤 그 설계가 맞는지, 숨기려던 값이 정말 숨겨지는지를 도메인 지식 없이 LLM 검토에만 기대게 됩니다. 이 프로젝트를 시작한 사람이 직접 겪은 실수입니다.

**기존 도구로 안 되는 부분.**
- Compact 컴파일러는 `disclose()` 없이 숨긴 값이 공개되는 것을 막습니다. 하지만 해시와 커밋은 "숨겨진다"고 믿고 통과시킵니다. 작은 값을 해시해 공개하는 것, 상수 소금 커밋, `ownPublicKey()`를 장부에 쓰는 것도 컴파일됩니다(근거: [design-guide.md](design-guide.md) "컴파일러가 막는 것과 통과시키는 것").
- midnight-expert의 `/audit-compact`는 LLM이 코드를 읽고 의심 가는 곳을 찾은 뒤, 심각한 것만 실행으로 확인합니다. 위협 카탈로그를 보면 권한 항목은 실행 확인이 "Yes"지만, 개인정보 항목은 "Sometimes"이거나 "No (review judgment)"입니다(9번 소금 없는 커밋, 10번 소금 재사용, 16번 과다 공개, 17번 assert 메시지). 확인용 시험도 프로젝트에 남지 않습니다.

**하는 일.** 그 빈 곳을 채웁니다.
1. 설계 단계에서 무엇이 드러나도 되는지 정하게 합니다.
2. 실제 계약을 실행해서 그 설명이 맞는지 판정합니다. LLM은 판정하지 않습니다.
3. 결과를 그림으로 보여 주고, 프로젝트에 남는 시험으로 만듭니다.

**대상.** 처음 Midnight를 쓰는 개발자(온라인 제출형 해커톤 참가자 포함)와, 제출물을 보는 심사위원·멘토.

**최종 형태.** 단독 레포로 먼저 만들고, 로컬 성능 시험(`proofkit bench`)을 통과하면 midnight-expert(`midnightntwrk/midnight-expert`, Midnight Foundation 공식 레포)에 새 플러그인으로 PR합니다. 폴더 구조를 midnight-expert에 맞춰 두어서, PR은 `plugins/proof-kit/`와 `packages/proof-kit/` 두 폴더를 옮기는 일이 됩니다.

## 2. 기능 세 가지

| 기능 | 하는 일 | 결과물 |
| --- | --- | --- |
| 설계 제안 `/proof:spec` | 숨길 값, 드러나도 되는 사실, 연결되면 안 되는 행동, 보증 주체를 묻습니다. 시험이 실패하면 고칠 패턴을 냅니다. | `privacy-spec.json` (누출 설명) |
| 공격 시험 `/proof:attack` (메인) | 시뮬레이터로 계약을 실행해 공격합니다. | `attack-plan.md`, `proof-attack.test.ts`, `privacy-baseline.json` |
| 시각화 `/proof:map` | "숨긴 값 → 회로 → 체인에 남는 것"을 4색으로 그립니다. 못 돌린 회로는 회색입니다. | README "Privacy" 절의 Mermaid 그림 |

세 기능은 Kachina 논문의 틀로 이어집니다. 계약은 "하는 일(∆)"과 "드러나는 것(Λ)"이고, 사용자는 누출 설명을 보고 승인합니다. 설계 제안이 누출 설명을 쓰고, 공격 시험이 그 설명이 정확한지 실행으로 확인하고, 시각화가 확인된 설명을 보여 줍니다. 자세한 구조는 [design-guide.md](design-guide.md)에 있습니다.

## 3. 공격 설계

공격자는 세 부류로 봅니다.
- 체인 관찰자: 공개 트랜스크립트, 장부 상태, 불린 회로, 거래 순서를 봅니다.
- 참여자: witness나 인자를 조작합니다.
- 배경지식을 가진 사람: 값 범위, 집단 크기를 압니다.

| 공격 | 내용 | 상태 |
| --- | --- | --- |
| A1 노출 | 숨긴 입력 하나만 바꿔 실행하고, 공개 트랜스크립트와 장부를 비교합니다. | 구현됨 |
| A2 역산 | 숨긴 입력에 결정적으로 묶인 공개 값이면, 값 범위를 전수 대입합니다. | 구현됨. 회로 밖 해시를 `assert`로 확인하는 경우는 다음 작업 2 |
| A3 연결 | 같은 사용자의 두 행동이 공개 값으로 이어지는지 봅니다. | 3주차 |
| A4 차분·집계 | 집계 전후 비교로 한 사람의 값을 알아냅니다. | 설계표만. 5주차부터 |
| A5 경로 | 숨긴 입력에 따라 불린 회로나 건드린 장부 칸이 달라지는지 봅니다. | 구현됨 |
| A6 재조합 | k-익명성, 용도 외 재사용 | 설계표만. 5주차부터 |
| T2 분할 witness | 한 호출 안에서 여러 번 읽는 witness에 읽을 때마다 다른 값을 줘도 회로가 통과하는지 실행으로 봅니다(`UNBOUND`, 기준 10). | 구현됨(2026-11-24). 결정 기록 11/24 참고 |
| T1~T3 보증(나머지) | 사칭(`ownPublicKey()`), 그 밖의 거짓 witness, 호출자가 주는 시각 | 제외. 결정 기록 2026-11-19 참고 |

소금(무작위 값)은 비교하는 실행끼리 고정해 둡니다. 그다음 소금만 바꿔 한 번 더 돌려서, 가려지는지 확인합니다.

**범위 밖**: 수수료 주소, 비차폐 토큰, 네트워크 정보, 지갑·증명 서버. 다음 단계에서 다룹니다.

## 4. 판정

- **판정은 시뮬레이터 실행 결과로만 합니다.** LLM이나 사람이 판정하지 않습니다. 실패는 실행으로 재현된 것만 내고, "의심" 경고는 내지 않습니다.
- **통과는** "이 공격 목록에서 재현되지 않음"이라는 뜻이지, "안전"이라는 뜻이 아닙니다.
- **판정 규칙**(2026-11-23 결정): 누출 설명에 없는 것이 드러나면 실패입니다.
  - 누출 설명 파일이 없으면 코드가 직접 `disclose()`한 것은 "공개" 색으로 칠합니다.
  - 해시나 커밋에서 값이 풀리는 것은 설명이 있든 없든 실패입니다.
  - 자세한 규칙은 [design-guide.md](design-guide.md) 5장과 `plugins/proof-kit/skills/proof-attack/references/verdicts.md`에 있습니다.
- **엔진 상태**: 위 규칙이 엔진에 들어가 있습니다(2026-11-24). 엔진은 실행 중 해시·커밋 출력을 기록해 직접 공개와 구분하고(`derived`), `privacy-spec.json`을 읽습니다(`--spec`).

## 5. 쓰이게 만드는 장치

- 시험은 일반 vitest 파일로 프로젝트에 남깁니다. midnight-cq `quality-init`이 이미 까는 Husky pre-push(`vitest run`)와 CI에서, 플러그인 없이도 돕니다.
- 래칫 기준선을 둡니다. 첫 실행은 막지 않고 기준선만 저장합니다. 기존 위험은 그림에 위험 색으로 남기고, 이후에는 새 위험만 실패로 냅니다.
- 위험을 넘기려면 `proofkit accept <항목> --reason "…"`을 씁니다. 이유는 README "의도한 공개" 목록에 들어갑니다.
- Stop 훅 게이트를 둡니다(compact-core Stop 훅 방식, 쿨다운 포함). PostToolUse 훅은 컴파일 뒤 3줄 요약을 냅니다.
- 설정 없이 동작합니다. 누출 설명 파일이 없으면 모든 witness와 회로 인자를 숨긴 값으로 봅니다. 값 범위는 타입에서 정합니다(Boolean, enum, 작은 Uint는 전수 대입). `Bytes`와 `Field`는 기본적으로 고엔트로피로 보지만, 이름에 `pin`, `age`, `amount` 같은 말이 있으면 작은 범위로 짐작합니다. 짐작은 공격 범위를 고를 때만 쓰고, 판정은 실행 결과로 합니다. 하네스는 프로젝트의 시뮬레이터가 있으면 재사용하고(계획), 없으면 `contract-info.json`으로 만듭니다.
- 결과가 제출물이 되게 합니다. README "Privacy" 절, 심사위원·멘토용 `proofkit report <레포>`.

## 6. 지킬 것

- 남의 레포에서 찾은 구멍은 작성자에게 먼저 알립니다. 보고서와 글에는 레포 이름을 싣지 않습니다.
- 남의 레포에 대한 정답표와 측정 결과는 이 공개 레포에 올리지 않습니다. 시연에 쓰는 나쁜 예는 직접 만든 코드로 합니다.
- 실제 사람 정보나 남의 말을 지어내지 않습니다. 근거 없는 수치를 쓰지 않고, 확인하지 못한 것은 "확인 못 함"이라고 씁니다.
- 커밋·푸시는 사용자가 요청할 때만 하고, main에 직접 올리지 않습니다.
- midnight-expert 기여 요건을 처음부터 지킵니다: Apache-2.0 머리말, DCO 서명, 단위·통합 시험, 문서. DCO 서명(`git commit -s`)은 코드를 내는 사람 본인이 해야 하므로, PR 때 사용자가 `git rebase --signoff`로 합니다.

주차 날짜는 원래 기획의 1주차(11/16~22)에서 7일씩 이어 계산했습니다. 2026-11-23은 2주차 첫날입니다.

**기준선 실험**
- (1) Claude Code + midnight-expert만으로 시나리오 4개(익명 투표, 봉인 입찰 경매, 나이·신용 자격 증명, 그리고 개발에 쓰지 않을 1개)를 각 2회 만들고, 고정 점검표로 구멍 수를 셉니다.
- (2) `/audit-compact`로 고친 결과를 봅니다.
- (3) 우리 도구를 쓴 결과를 봅니다.

**관문**
- 1주차 최근 레포 측정: 숨김 구멍이 드물면 보증 공격 T1~T3 비중을 키웁니다. T1~T3를 제외한 결정과 충돌하므로 미결입니다(14절). 측정 결과 숨김 구멍은 드물었습니다(12절).
- (1)에서 구멍이 거의 없으면 엔진을 midnight-expert 기여로 좁힙니다. **(1)은 아직 하지 않았습니다.** 엔진 작업은 (1)과 별개로 진행했지만, 방향을 좁힐지는 (1)의 결과를 보고 정합니다.
- (2)가 숨김 구멍까지 다 잡으면, 우리 몫은 자동 게이트 + 남는 시험 + 시각화로 좁힙니다.

## 9. PR 조건 (`proofkit bench`)

- 찾아내기: 시나리오 10쌍 이상에서 정답 구멍을 모두 찾습니다.
- 헛것 0: 고친 판과 단단한 수상작에서 실패가 나오면 안 됩니다.
- 처음 보는 레포: 2026-11-17 이후 공개된 레포 10개 이상(커밋 고정, 사람 판정)에서, 실패 판정 중 실제 구멍이 80% 이상이어야 합니다.
  - 개발 중에 본 레포로 평가하지 않기 위해, 1주차 측정은 11/17 이전 레포로만 했습니다.
- 설정 없이 80% 이상 동작해야 합니다. "시험 못 함"은 따로 셉니다.
- 회로 하나를 바꾼 뒤 재실행은 30초 이하여야 합니다.
- 플러그인 없이 `npm test`와 pre-push에서 돌아야 합니다.
- 3회 결과가 같아야 합니다.
- 보고서 `bench-report.md`를 PR 본문에 넣습니다.

## 10. 진행 상황 (2026-11-24, 판정 규칙 반영 후)

**완료**
- 스파이크: 트랜스크립트로 A1·A2·A5를 확인했습니다. 한 쌍 실행에 17ms, 결과는 결정적입니다.
- 레드팀 검증: 스파이크의 가정을 깨는 계약을 직접 만들어 실행했고, 결과를 엔진에 반영했습니다.
  - 실행 한 쌍으로는 `secret > 100` 같은 부분 노출을 놓칩니다 → 경계값과 소스의 상수를 넣어 여러 번 실행합니다.
  - 소유자 확인이 있는 회로는 호출 때만 비밀을 바꾸면 거부됩니다 → 생성자부터 같은 값으로 다시 실행합니다.
  - 소금 커밋, 고엔트로피 키의 해시도 차이를 냅니다 → 차이를 가림·태그·복원·부분 노출로 나눕니다.
  - 기본값대로면 `Bytes<32>` PIN은 고엔트로피로 분류돼 역산 공격을 건너뜁니다 → 이름 힌트와 저엔트로피 사전을 씁니다.
  - 반환값으로 새는 것을 실패로 보려 했으나, 공식 문서상 반환값은 체인에 남지 않아 정정했습니다.
- 엔진(`packages/proof-kit`)
  - A1·A2·A5, 소금 가림 판정, 부분 노출 판정, T2 분할 witness(2026-11-24)
  - 설정 없이 시작 상태 찾기: 생성자 인자 맞추기, 회로를 두 개까지 먼저 부르기, witness 사이의 관계 맞추기
  - CLI `proofkit attack`

- 분할 witness 공격(T2, 2026-11-24): 한 호출에서 두 번 이상 읽힌 witness마다, 첫 읽기 또는 나머지 읽기에 다른 값을 주고 돌립니다. 통과하면 `UNBOUND` 실패입니다. 시나리오 `split-witness`가 정답표로 확인하고, 고치기 전 판 3쌍의 7개 읽기를 모두 잡습니다. 시험 계약 vault의 `register()`에서도 하나 찾았습니다(PIN 해시와 커밋이 서로 다른 PIN을 담을 수 있음).

1. **(완료 2026-11-24) 판정 규칙과 누출 설명을 엔진에 반영합니다.**
   - 해시·커밋 구분: 실행 중 런타임의 해시·커밋 함수(`persistentHash`, `persistentCommit`, `transientHash`, `transientCommit`) 출력을 기록합니다. 그리고 달라진 공개 값이 그중 하나인지 봅니다. 컴파일된 계약의 런타임 import를 감싼 사본을 불러오는 방식으로 기록합니다.
   - 누출 설명 전달: CLI에 `--spec <file>`을 추가합니다. 없으면 계약 소스와 같은 폴더의 `privacy-spec.json`을 찾습니다. 시나리오는 시나리오 폴더의 `privacy-spec.json`을 `--spec`으로 넘깁니다.
   - 출력: finding에 `disclosure` 필드를 추가합니다.
     - `"declared"`: 설명 없이, 직접 `disclose()`한 것
     - `"spec"`: `mayReveal`이 덮은 것
     - `null`
     - `disclosure`가 있으면 `failure: false`이고, 그림에서는 "공개" 색입니다.
   - `mayReveal` 대조: 회로 + 입력 + 종류로만 맞춥니다. `kind: "value"`는 EXPOSED와 RECOVERABLE을, `"fact"`는 PARTIAL을, `"path"`는 `where: "path"`를 덮습니다. `fact`의 조건식은 사람이 읽는 설명이고, 엔진은 해석하지 않습니다.
   - `range "lo..hi"`는 양끝을 포함합니다.
   - 완료 기준(정답표 대조 규칙):
     - 구멍 판: `answer.json`의 각 finding(circuit, input, attack, kind, where)이 실패로 나와야 합니다.
     - 고친 판: 실패가 0이어야 합니다.
     - 두 판 모두 `intendedDisclosures`의 항목은 실패가 아니어야 합니다.
     - 시나리오는 컴파일된 파일을 저장하지 않으니, compactc 0.36.0이 필요합니다(CI에는 있음).
2. **(완료 2026-11-24) 시각화(`/proof:map`).** 엔진 JSON으로 "숨긴 값 → 회로 → 체인에 남는 것" Mermaid 그림을 4색(숨김·증명만·공개·위험, 회색 시험 못 함)으로 그립니다. 구멍 판과 고친 판을 나란히 보여 줍니다.
   - 완료 기준: 건강 정보 예제의 두 판 그림에서 구멍 판은 나이·질병 코드가 위험 색, 고친 판은 증명만 색입니다.

3. **A2 보완(assert 오라클).** 회로 밖에서 만든 해시를 회로 안에서 `assert(hash(witness) == 저장값)`으로만 확인하는 계약이 대상입니다. 공격자는 후보를 넣어 회로를 돌려 보고, 통과하는 후보를 찾습니다. 엔진도 이 방식을 씁니다.
