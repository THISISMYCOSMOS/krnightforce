# 처음 만들 때 생기는 일: 실제 구축 기록에서 일반화한 교훈

**출처**: 프로젝트 사용자가 2026년 9월 Midnight 해커톤에서 직접 만든 앱의 개발 기록입니다. 기획부터 회로 설계, LLM 검토 3회와 통합 검토까지 담겨 있습니다.
- 앱 내용: 운전 기록으로 보험 할인 자격을 증명하는 앱
- 이 문서에는 원문, 팀원 이름, 저장소 정보를 싣지 않습니다. 일반화한 교훈만 적습니다.

**대상 독자**: Midnight를 처음 쓰는 사람. 각 교훈은 다음 순서로 적습니다.
1. **그때**: 기록에서 실제로 있었던 일
2. **규칙**: 일반화한 내용
3. **다른 앱에서는**: 이 저장소의 예제에 적용하면 어떻게 되는가
4. **확인**: 엔진이 실행으로 확인하는지

기준 번호는 `plugins/proof-kit/skills/proof-spec/references/criteria.md`, 패턴 이름은 같은 폴더의 `patterns.md`를 가리킵니다.

---

## A. 기획 단계: 무엇을, 누구에게

### 1. "보여 준다"에는 두 청중이 있다

- **그때**: 팀은 보험사에 정확한 점수와 거리를 주기로 했습니다. 그러면서도 공개 장부에는 커밋과 중복 방지 값만 남기기로 했습니다.
  - 처음에는 이 둘이 한 문장("점수는 정확한 숫자로")에 섞여 있었고, 나중에 두 줄로 나뉘었습니다.
- **규칙**: 공개 대상은 셋입니다.
  - **누구나**: 공개 장부에 올라갑니다.
  - **한 검증자에게만**: 장부에는 `persistentCommit(값, nonce)`만 두고, 검증자에게는 opening(값 + nonce)을 장부 밖으로 건넵니다. 검증자는 opening으로 커밋을 다시 계산해 장부의 값과 대조합니다.
  - **본인만**: 장부에 올리지 않습니다.
- **다른 앱에서는**:
  - 장학금: 장학팀은 소득 비율을 알아도 되지만 공개 장부는 "100% 이하"라는 사실만 압니다.
  - 차 동호회: 운영자는 차번호를 알지만 회원 명단을 보는 사람은 모릅니다.
- **확인**: 엔진은 "누구나"만 봅니다. "검증자에게만"은 장부 밖이라 시험 대상이 아닙니다. 그래서 설계안에서 따로 적게 했습니다(`data-inventory.md`의 "Who may see it" 열).

### 2. 증명이 보장하지 않는 것을 먼저 적는다

- **그때**: 사용자가 처음부터 경계를 못 박았습니다.
  - "해시나 커밋먼트만 생성한 것을 ZK 검증으로 표현하지 않는다."
  - "운행이 실제로 있었는지, 빠짐없이 냈는지, 원본이 삭제됐는지는 ZK가 보장하지 않는다."
  - 이 경계 덕분에 LLM이 과장된 완료 보고를 할 때 바로 잡아낼 수 있었습니다.
- **규칙**: 증명은 "회로가 받은 입력으로 올바르게 계산했다"는 것만 보장합니다. 다음은 보장하지 않습니다.
  - 입력이 현실에서 일어났는지
  - 입력을 전부 냈는지
  - 같은 입력을 두 번 내지 않았는지 (계약이 기록하지 않는 한)
  - 장부 밖 사본이 지워졌는지
- **다른 앱에서는**:
  - 건강 정보: 나이가 진짜인지는 발급자(병원)가 보증합니다(기준 10). 증명이 보장하지 않습니다.
  - 차 동호회: 등록증 확인은 운영자 몫입니다.
- **확인**: 엔진이 확인할 수 없는 영역입니다. 설계안 2번(누출 설명)에 함께 적게 했습니다(`design-output.md`).

### 3. 말하지 않은 메타데이터: 개수, 진행, 횟수

- **그때**: 기록 하나마다 트랜잭션을 하나씩 냈습니다. 공개 장부에는 기록 수, 진행 커서, 회차(revision)가 있었습니다. 그래서 운행마다 기록 수와 전체 운행 횟수가 누구에게나 보였습니다. 검토에서 "의도한 공개"로 정리했지만, 기획 때는 아무도 말하지 않은 정보였습니다.
- **규칙**: 정보 목록에 "처리 메타데이터"를 따로 넣습니다. 몇 번에 나눠 내는지, 진행 카운터, 버전 번호가 그 대상입니다.
- **다른 앱에서는**:
  - 장학금: 회차별 신청자 수(카운터)가 공개됩니다. 누출 설명의 "받아들이는 누출"에 적었습니다.
  - 투표: 투표 수 카운터가 공개됩니다.
- **확인**: 카운터 값이 숨긴 입력에 따라 달라지면 엔진이 A1·A5로 잡습니다. 입력과 무관한 개수(트랜잭션 수)는 잡지 않습니다.

### 4. 배포 단위가 곧 연결 단위다

- **그때**: 계약 하나가 규칙 하나와 가입자 하나(Scope)를 고정했습니다. 그래서 가입자마다 계약 주소가 따로 생겼고, 한 계약 주소가 그 가입자의 모든 운행을 묶었습니다.
  - 이 앱에서는 보험사가 가입자를 이미 알아서 받아들일 수 있었습니다.
  - 하지만 익명이 필요한 앱이라면 설계가 처음부터 틀린 것입니다.
- **규칙**: "누구 단위로 계약을 배포하는가"를 정보 목록에서 묻습니다. 사용자별 배포는 사용자별 연결입니다.
- **다른 앱에서는**: 차 동호회와 장학금은 계약 하나에 모든 회원이 들어갑니다. 회원끼리 계약 주소로 구분되지 않습니다.
- **확인**: 엔진 밖입니다(배포 구조). 설계 질문으로만 다룹니다.

### 5. "한 번만"의 단위를 정한다

- **그때**: 중복 신청 방지 값(nullifier)을 "확정된 상태"에 묶었습니다.
  - 상태가 바뀔 때마다 새 nullifier가 생겨서, "평가 기간당 한 번"은 체인에서 강제되지 않았습니다. 검토에서 지적됐고, 기간당 제한은 백엔드 몫으로 남았습니다.
  - 같은 운행 데이터를 다시 내는 것도 회로가 막지 않았습니다. 누적 거리가 두 배가 될 수 있었습니다.
- **규칙**: nullifier에는 "한 번"의 단위를 정확히 넣습니다. 기간당 한 번이면 `hash([태그, 기간, 비밀])`입니다. 체인 밖에서 막는다면 그렇다고 설계에 적습니다.
- **다른 앱에서는**: 장학금은 단위가 "회차당 한 번"이라 `hash([태그, 회차, 자격 증명 비밀])`로 만들었습니다.
- **확인**: 회차 간 연결은 A3(예정)에서 확인합니다. nullifier에 학번처럼 경우의 수가 적은 값이 들어가면 A2가 잡습니다(장학금 구멍 판).

## B. 회로 단계

### 6. 비밀 witness는 한 번만 읽는다 (가장 심각했던 문제)

- **그때**: 최종 신청 회로가 소유자 비밀을 두 번 불렀습니다. 한 번은 소유자 확인에, 한 번은 nullifier 계산에 썼습니다.
  - 검토 LLM이 "두 호출은 서로 다른 비공개 입력"이라고 지적했지만, 코드를 읽기만 해서는 확정하지 못했습니다("컴파일 결과를 봐야 확인됨").
  - 정직한 witness로 돌린 시험은 모두 통과했습니다.
- **규칙**: 회로 안에서 같은 witness를 두 번 부르면 입력이 두 개가 됩니다. 증명하는 사람이 두 번째 호출에 다른 값을 넣을 수 있습니다. 한 번 읽어 지역 변수로 재사용해야 합니다.
- **실행으로 확인함**: 실험 계약 p29(두 번 읽기)와 p29b(한 번 읽기)를 컴파일해 돌렸습니다(`docs/design-guide/compiler-probe/`).
  - 첫 호출에는 진짜 비밀, 두 번째 호출에는 새 값을 주는 witness를 썼습니다.
  - p29는 같은 소유자, 같은 범위의 신청이 3번 모두 통과했습니다.
  - p29b는 3번 모두 거부됐습니다.
  - 검토 LLM이 읽기만으로 확정하지 못한 문제를 실행으로 확정한 사례입니다.
- **다른 앱에서는**: 우리 예제 셋(건강 정보, 차 동호회, 장학금)에 같은 실수가 있었습니다. 아래 점검표 다음의 표를 보세요.
- **확인**: 엔진 공격 **T2(분할 witness)**가 실행으로 확인합니다(2026-11-24 추가). 결과 종류는 `UNBOUND`, 기준은 10입니다.
  - 한 호출 안에서 두 번 이상 읽힌 witness마다, 첫 읽기나 나머지 읽기에 다른 값을 주고 회로를 돌립니다.
  - 그래도 통과하면 실패입니다.
  - 정답표 시나리오: `bench/scenarios/split-witness`

### 7. 결과를 받지 말고 회로 안에서 다시 계산한다

- **그때**: 처음 단계의 계약은 "이전 커밋 → 새 커밋" 교체만 확인했습니다. 점수는 서버가 계산해 넘겼습니다.
  - 사용자가 "커밋만 만든 것을 ZK 검증이라고 하지 말 것"이라고 정해 둔 덕분에, 다음 단계에서 회로가 누적 합과 점수 산식을 직접 다시 계산하게 바꿨습니다.
- **규칙**: 커밋은 값을 고정할 뿐, 계산이 맞는지는 증명하지 않습니다. 원재료나 이전 상태의 opening을 witness로 받아, 회로 안에서 다시 계산하고 후보 값과 같은지 `assert`합니다.
  - 누적 합에는 범위를 확인하는 `Uint` 변환을 씁니다. `Field`를 쓰면 값이 한 바퀴 돌아 작은 값이 될 수 있습니다.
- **다른 앱에서는**:
  - 장학금의 "100% 이하"는 회로가 소득 비율로 직접 비교합니다.
  - 차 동호회의 "1년 이상"도 회로가 구매월과 동호회 달로 계산합니다.
- **확인**: 보증 문제(기준 10)라 엔진의 숨김 공격 밖입니다.

### 8. 하나가 들어 있다는 것과 전부 처리했다는 것은 다르다

- **그때**: Merkle 포함 증명만으로는 "기록을 빠짐없이, 순서대로, 한 번씩 합산했다"를 보장하지 못했습니다. 그래서 다음 장치를 넣었습니다.
  - 기록 개수를 leaf 안에 넣기
  - 매 단계 `순번 == 경로 위치 == 커서` 확인
  - `커서 == 개수`일 때만 확정
  - leaf와 내부 노드에 서로 다른 도메인 태그 사용
- **규칙**: 멤버십 증명과 완전성 증명을 구분합니다. 해시 종류마다 다른 도메인 태그를 씁니다.
- **확인**: 보증 문제라 엔진 밖입니다. `patterns.md`의 "All records, not just one"에 정리했습니다.

### 9. 검증자가 나중에 다시 볼 값은 덮어쓰지 않는다

- **그때**: 결과 커밋을 장부 한 칸에 두고 새 신청마다 덮어썼습니다. 보험사가 저장해 둔 예전 신청의 opening은 더 이상 장부와 맞지 않게 됐습니다.
- **규칙**: 검증자가 다시 확인할 값은 신청별 키(nullifier)를 가진 `Map`에 둡니다.
- **확인**: 엔진 밖입니다.

### 10. 생성자에 고정한 값은 바뀌지 않는다

- **그때**: 규칙 해시를 생성자에서 고정했습니다. 그래서 보험사가 규칙 v2를 등록하자 기존 상태가 v1에 묶여 운행과 신청이 모두 막혔습니다.
- **규칙**: 배포 전에 "바뀔 수 있는 값인가"를 정합니다. 바뀐다면 권한 있는 재연결 회로를 처음부터 둡니다.
- **다른 앱에서는**: 건강 정보·차 동호회·장학금의 발급자·운영자 키도 생성자에 고정돼 있습니다. 키를 바꿔야 하는 날이 오면 같은 문제가 생깁니다.

### 11. 모든 입력을 witness로 두면 지갑이 무엇을 승인하는지 보여 줄 수 없다

- **그때**: 회로에 공개 인자가 하나도 없었습니다. 그래서 지갑 승인 화면에 "이전·다음 상태 커밋"을 보여 줘도, 지갑이 그 값을 트랜잭션에서 확인할 방법이 없었습니다.
  - 결국 "어댑터가 제공한 값"이라고 표시하는 것으로 정리했습니다.
- **규칙**: 숨김과 동의의 투명성은 서로 당깁니다. 사용자가 무엇에 서명하는지 지갑이 보여 줘야 한다면, 그 값만은 공개 인자나 공개 출력으로 두는 것을 검토합니다.

## C. 검증 단계

### 12. 증거의 단계를 나눠 부른다

- **그때**: 사용자는 다음을 각각 다른 결과로 기록하게 했습니다.
  - 정적 읽기
  - 컴파일
  - 회로 실행 시험
  - 실제 증명
  - 체인 반영
  - 지갑 연결 종단 시험
- 검토 LLM의 세 차례 검토는 모두 "소스 읽기"였고, 한 번은 아무것도 실행하지 못했다고 스스로 밝혔습니다.
- **규칙**: "통과"라고 말할 때 어느 단계인지 붙입니다. proof-kit 엔진은 **컴파일된 회로의 실행** 단계입니다. 증명 서버, 체인, 지갑 단계는 아닙니다.

### 13. 정직한 witness로만 돌린 시험은 악의적인 witness를 못 잡는다

- **그때**: 6번의 문제가 있던 판도 실제 체인에서 "중복 신청 거부"가 통과했습니다. 그 시험이 정직한 witness만 썼기 때문입니다.
- **규칙**: witness는 사용자가 마음대로 바꿀 수 있는 코드입니다. 시험에는 witness를 일부러 다르게 주는 경우가 있어야 합니다.
- **연결**: 이것이 proof-kit의 출발점입니다. 엔진은 witness 값을 바꿔 가며 공개 장부의 차이를 봅니다(A1·A2·A5). 6번 실험은 같은 생각을 "같은 witness의 호출마다 다른 값"으로 넓힌 것입니다.

| 2. 보장 안 하는 것 | 나이가 진짜인지: 병원이 보증 | 등록증: 운영자가 확인 | 소득 서류: 장학팀이 확인 | 투표권 자격: 등록자가 보증 |
| 3. 메타데이터 | 발급·확인 횟수 | 등록 차 수 | 회차별 신청자 수 | 투표 수 |
| 4. 배포 단위 | 계약 하나 | 계약 하나 | 계약 하나 | 투표마다 하나면 투표 간 연결 없음 |
| 5. "한 번"의 단위 | 해당 없음 | 해당 없음 | 회차당 한 번 | 투표당 한 번 |
| 6. witness 한 번 읽기 | **두 번 읽고 있었음** → 고침 | **세 회로가 두 번 읽고 있었음** → 고침 | **`apply()`가 두 번 읽고 있었음** → 고침 | 한 번 |
| 10. 생성자 고정 | 발급자 키 | 운영자 키 | 장학팀 키 | — |

**이 교훈을 우리 예제에 적용하다 찾은 것**: 이 점검표를 만들면서 우리 예제부터 확인했더니, 고친 판 7쌍 중 3쌍이 6번과 같은 모양이었습니다.

| 예제 | 회로 | 두 번 읽은 witness | 그 결과 |
| --- | --- | --- | --- |
| 건강 정보 | `verifyAdult` | `patient_age()` | 10살이 "18세 이상" 확인을 통과함 (실행으로 확인) |
| 차 동호회 | `showCar` | `car_model()` | 등록과 다른 모델을 공개할 수 있음 |
| 차 동호회 | `proveHeldYear` | `purchase_month()` | 1년 배지를 위조할 수 있음 |
| 차 동호회 | `registerCar` | `operator_secret()`, `plate_number()` | 중복 방지 태그를 우회할 수 있음 |
| 장학금 | `apply` | `income_pct()`, `cred_nonce()` | 소득이 높은 학생이 통과하고, 한 회차에 여러 번 신청할 수 있음 |

- 우리 숨김 시험은 이것을 잡지 못했습니다. 숨김이 아니라 보증의 문제이기 때문입니다.
- 지금은 모두 "한 번 읽고 값으로 넘기기"로 고쳤습니다. 진단 스크립트 `packages/proof-kit/scripts/count-witness-reads.mts`로 다시 확인했습니다.
  - 고치기 전 판: 위 5개 회로의 두 번 읽기 7개를 정확히 짚었습니다.
  - 고친 뒤: 0개입니다.
- 같은 실수를 LLM(이 문서를 쓴 Claude 포함)도 여러 번 했다는 점이 이 교훈이 처음 하는 사람에게 중요한 이유입니다.
