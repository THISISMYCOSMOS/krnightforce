# FAQ: Midnight를 모르는 LLM이 같은 결과를 못 내게 하려면

질문은 하나입니다. Midnight Proof Kit이 내는 결과 중 Midnight를 모르는 일반 LLM도 똑같이 낼 수 있는 것은 무엇이고, 그렇지 않게 만들려면 무엇을 해야 하는가. 근거가 되는 파일 경로를 함께 적었습니다. 확인하지 못한 것은 "확인 못 함"으로 적었습니다.

---

## 1. 지금 상태

### Q1. 일반 LLM도 똑같이 만들 수 있는 것은?
솔직히 꽤 있습니다.
- **정보 목록(1b단계)의 일반적인 부분.** "차량 번호, 실소유주, 주소는 민감하다"나 "사진에 번호판·위치가 담길 수 있다" 같은 내용은 일반 개인정보 상식입니다(`plugins/proof-kit/skills/proof-spec/references/data-inventory.md`).
- **일반 설계 조언.** "필요한 사실만 공개", "같은 식별자를 여러 곳에 쓰면 이어진다"는 Midnight가 아니어도 나오는 말입니다.
- **설계안 문장 자체.** 설계안은 스킬 문서를 따라 LLM이 씁니다(`references/design-output.md`). 형식이 고정돼 있을 뿐, 쓰는 주체는 LLM입니다.
- **용어 설명.** 공식 문서를 읽은 LLM이면 비슷하게 설명할 수 있습니다(`references/midnight-terms.md`). 다만 그 LLM이 0.36.0에서 실제로 어떻게 동작하는지 확인했다는 보장은 없습니다.

### Q2. 일반 LLM이 못 만드는 것은?
코드를 읽고 추론해서는 나오지 않는 것들입니다.
- **실행으로 낸 판정.** 엔진은 컴파일된 계약을 로컬 런타임에서 실제로 돌립니다. 숨긴 입력을 바꿔 가며 공개 트랜스크립트를 비교하고, 값을 대입해 되찾습니다. 실패마다 재현할 수 있는 증거가 있습니다(`packages/proof-kit/src/attack.ts`).
- **해시를 거쳤는지 실행으로 구분(`derived`).** 실행 중 `persistentHash`, `persistentCommit`, `transientHash`, `transientCommit`의 출력을 기록하고, 달라진 공개 값이 그 출력인지 확인합니다(`src/harness.ts`). LLM은 코드를 읽고 "해시 같다"고 짐작할 뿐입니다.
- **컴파일러로 확인한 사실.** 0.36.0으로 직접 컴파일한 실험 계약 40개(p01~p29와 변형)와 결과가 있습니다(`docs/design-guide/compiler-probe/`). 예를 들어 `persistentCommit`은 상수 소금이어도 `disclose()` 없이 통과하고(p05b), `blockTimeGte`는 비교 시각을 공개합니다(p28).
- **설정 없는 시작 상태 찾기.** pure 회로·해시로 생성자 인자를 맞추고, 필요한 회로를 먼저 불러서 실행 가능한 상태를 찾습니다(`src/setup.ts`).
- **정답표 대조.** 구멍 판 / 고친 판 8쌍이 정답표대로 나오는지 시험이 자동으로 확인합니다(`bench/scenarios/`, `packages/proof-kit/test/bench.test.ts`).
- **실측 수치.** 비공개 표본 13개 레포에서 새 판정 규칙을 적용하니 실패가 193건에서 2건으로 줄었고, 남은 2건은 사람이 판정한 진짜 구멍이었습니다(`docs/plan.md` 12절).

### Q3. 그럼 겹치는 부분은 문제인가?
설계 조언만 놓고 보면 겹칩니다. 차이는 **그 조언이 맞는지 실행으로 확인되느냐**에서 납니다. 그래서 차별화의 방향은 하나입니다. LLM이 쓴 문장마다 실행 근거(실험이나 엔진 결과)를 붙이고, 근거가 없는 문장은 "안내"로 낮추는 것입니다.

## 2. 차별화를 키우기 위해 할 일

각 항목: 무엇 / 일반 LLM이 못 하는 이유 / 확인 방법 / 상태.

### Q4. 스킬의 모든 주장에 근거를 붙인다
- **무엇**: 스킬과 가이드의 "컴파일됨 / 막힘 / 샘" 주장마다 실험 번호(p..)나 엔진 결과를 붙입니다.
- **이유**: LLM의 기억은 버전이 섞여 있습니다. midnight-expert 문서도 "Last verified"가 0.31.1 기준이었습니다.
- **확인**: 실험 계약을 컴파일해서 결과가 `results.txt`와 같은지 봅니다.
- **상태**: 부분 완료. criteria.md와 design-guide.md의 함정에는 실험 번호가 붙어 있습니다. 모든 문장에 붙었는지는 점검하지 않았습니다.

### Q5. 실험을 CI에서 다시 돌려, 컴파일러가 바뀌면 알린다
- **무엇**: 실험 계약 40개를 CI에서 컴파일하고, 결과가 `results.txt`와 다르면 실패시킵니다. 새 컴파일러 버전이 나오면 같은 실험으로 표를 다시 만듭니다.
- **이유**: "지금 이 버전에서 이렇다"를 계속 보장하는 건 실행만 할 수 있습니다.
- **확인**: CI 결과
- **상태**: 제안. 지금 CI(`.github/workflows/ci-proof-kit.yml`)는 엔진 시험만 돌립니다.

### Q6. "되는 것 / 안 되는 것" 표를 실험에서 자동으로 만든다
- **무엇**: criteria.md의 표를 손으로 쓰지 않고, 실험 결과에서 만들어 냅니다.
- **이유**: 표와 실제 컴파일러 동작이 어긋날 수 없게 됩니다.
- **확인**: 생성 스크립트 + CI
- **상태**: 제안

### Q7. 실행으로 Midnight 특유의 함정을 더 찾는다
- **무엇**: 장부 연산과 표준 라이브러리 함수마다 "무엇이 공개되나"를 실험과 엔진으로 잽니다.
  - 이미 찾은 것: `blockTimeGte` 비교 시각 공개(p28), `ownPublicKey()` 저장 시 연결(p21), 커밋은 taint를 지우고 해시는 안 지움(p04/p05)
  - 더 볼 후보: `Map`·`Set`·`MerkleTree`·`HistoricMerkleTree` 연산별로 트랜스크립트에 무엇이 남는지(아래 Q8), `checkRoot` 결과를 분기에 쓸 때, `evolveNonce` 같은 함수
- **이유**: 공식 문서에 없거나 흩어져 있는 동작이라, 돌려 봐야 압니다.
- **확인**: 실험 계약 + 엔진 실행
- **상태**: 부분 완료(p29까지. p29는 witness를 두 번 읽는 회로를 실행으로 확인). 나머지는 제안

### Q8. 장부 타입별 공개 범위를 엔진으로 측정한다
- **무엇**: `MerkleTree.insert`는 `disclose()`가 필요하지만 잎이 숨겨진다고 문서에 적혀 있습니다(리서치 p15). 이런 주장을 엔진으로 직접 확인해 표로 만듭니다. 예: 삽입한 값이 트랜스크립트에 그대로 남는지, 경로가 남는지.
- **이유**: "필요한 `disclose()`"와 "실제로 드러나는 것"이 다른 경우는 실행해야 압니다.
- **확인**: 엔진 결과(`derived`, `where`)
- **상태**: 제안. 직접 측정하지 않았습니다.

### Q9. 설계안에서 컴파일되는 Compact 뼈대를 만들고, 바로 공격한다
- **무엇**: 정보 목록과 설계안(어디에 두나, 값마다 부품)으로 Compact 계약 뼈대를 만듭니다. 그리고 컴파일 → 엔진 공격 → 누출 설명과 대조까지 자동으로 이어서, 설계안 자체를 "실행으로 확인된 설계"로 만듭니다.
- **이유**: LLM이 만든 코드는 컴파일되는지도, 새는지도 모릅니다. 우리는 둘 다 실행으로 확인합니다.
- **확인**: 컴파일 성공 + 시험 실패 0
- **상태**: 제안. 지금은 건강 정보 예제만 손으로 같은 흐름을 따라갔습니다(`docs/design-guide/walkthrough-health-credential.md`).

### Q10. 고칠 패턴마다 공격으로 확인한 예제를 둔다
- **무엇**: patterns.md의 패턴마다 구멍 판 / 고친 판 쌍을 두고, 고친 판이 실제로 통과하는 것을 시험으로 보장합니다.
- **이유**: "이렇게 고치면 된다"는 LLM도 말하지만, 그 말이 맞는다는 보장은 실행만 줍니다.
- **확인**: `bench.test.ts`
- **상태**: 부분 완료. 8쌍(해시 커밋, 상수 소금, 사실만 공개, 경로, 건강 정보, 차 동호회, 장학금, 분할 witness)은 있습니다. nullifier·소유 증명·발급자 예제는 컴파일만 확인했고 공격은 없습니다(`docs/design-guide/examples/`).

### Q11. assert 오라클(A2 확장)
- **무엇**: 회로 밖에서 만든 해시를 회로 안에서 `assert`로만 확인하는 계약에서, 후보를 넣어 `assert`가 통과하는 값을 찾습니다.
- **이유**: 실제 해커톤 사례에서 나온 구멍이고, 지금 엔진도 놓쳤습니다. 코드를 읽어서는 "위험해 보인다"까지만 말할 수 있습니다.
- **확인**: 같은 유형의 직접 만든 시나리오에서 값을 복원하는지 봅니다.
- **상태**: 계획(`docs/plan.md` 11절 3번)

### Q12. A3 연결, A6 조합을 실행으로 확인한다
- **무엇**
  - A3: 같은 사용자의 두 행동을 실행해서 공개 값이 겹치는지 봅니다.
  - A6: 공개되는 속성들의 조합이 표본에서 몇 명으로 좁혀지는지 잽니다.
- **이유**: 지금 두 가지는 "안내"에 머물러 있어서, LLM의 일반 조언과 다르지 않습니다.
- **확인**: 시나리오 쌍(예: 범위 없는 nullifier vs 범위 섞은 nullifier)
- **상태**: A3는 계획(3주차), A6는 설계표만(5주차부터). A6를 어떻게 실행으로 잴지는 정해지지 않았습니다.

### Q13. 버전을 고정하고 다시 확인한다
- **무엇**: 모든 결과에 컴파일러(0.36.0)와 런타임(0.21.0) 버전을 적고, 버전이 바뀌면 실험과 bench를 다시 돌립니다.
- **이유**: 버전마다 동작이 다를 수 있다는 점을 근거로 보여 줄 수 있습니다.
- **확인**: 엔진 보고서에 버전 기록(구현됨). 시나리오 정답표에 `compilerVersion`(구현됨)
- **상태**: 부분 완료. 자동 재확인은 Q5와 같습니다.

### Q14. 실측 수치를 근거로 쓴다
- **무엇**: bench 수치를 PR·발표의 근거로 씁니다. 예: 표본 레포에서 실패 193 → 2, 남은 2건이 진짜 구멍, 고친 판 헛 판정 0.
- **이유**: LLM 리뷰는 같은 수치를 낼 수 없습니다.
- **확인**: `proofkit bench`(계획), 지금은 시험과 비공개 측정
- **상태**: 부분. 11/17 이후 처음 보는 레포로 다시 재야 합니다(PR 조건).

## 3. "LLM 판단 금지" 원칙과의 관계

### Q15. LLM은 그럼 무엇을 하나?
묻고, 정리하고, 설명합니다. 정보 목록, 질문, 설계안 문장, 함정 설명이 여기에 해당합니다. **통과·실패는 엔진만 정합니다.** 설계 기준도 "판정"(엔진이 확인)과 "안내"(확인하지 않음)로 나눠, 안내를 확인된 것처럼 말하지 않게 했습니다(`references/criteria.md`, SKILL.md 함정 3번).

### Q16. 차별화 작업이 원칙을 깨지 않나?
위 할 일은 전부 "LLM 문장을 실행 근거로 바꾸는" 방향이라 원칙을 강화합니다. 예를 들어 Q9의 뼈대 생성은 LLM이 하더라도, 그 뼈대가 맞는지는 컴파일과 공격으로 판정합니다.

## 4. 하지 않을 것과 정할 것

### Q17. 하지 않을 것
- LLM이나 사람이 코드를 읽고 "의심" 판정을 내는 것
- 보증 공격 T1~T3(midnight-expert와 겹쳐 제외, `docs/plan.md` 결정 기록). 예외로, 같은 witness를 여러 번 읽는 회로의 분할 witness 공격(T2)은 넣었습니다(11/24). midnight-expert가 읽기만으로 확정하지 못한 부분이기 때문입니다.
- 지갑, 증명 서버, 수수료(DUST)·비차폐 토큰, 네트워크 정보, 사진 같은 계약 밖 데이터의 판정. 안내만 합니다.
- Google Cloud TEE 연동(사용자 결정으로 제외)

### Q18. 사용자가 정할 것
1. Q9(설계안 → Compact 뼈대 생성 → 자동 공격)를 일정에 넣을지, 넣는다면 시각화 다음 순서로 둘지
2. Q5·Q6(실험 CI, 표 자동 생성)을 언제 할지. 작은 일이라 다음 작업 사이에 끼워 넣을 수 있습니다.
3. A6(조합 위험)를 실행으로 재는 방법을 연구할지, 계속 안내로 둘지
4. 장부 타입별 측정(Q8) 결과를 midnight-expert의 compact-privacy-disclosure 문서 수정 제안(이슈)으로 보낼지. 외부에 올리는 일이라 승인이 필요합니다.
